# Implementation Plan — Phase D6.4: Transformation Workflow Orchestration (Revised)

Phase D6.4 coordinates the transformation workflow after D6.1/D6.2 planning and D6.3 contracts/adapters. It converts an abstract `OutputPlan` into an executable task schedule and aggregates execution results, while keeping external engines (GenOffice D7 and Video Engine D8) strictly outside D6.4.

---

## 1. Architectural Positioning & The Single Execution Path

### The Single Authoritative Execution Path
To avoid competing pipelines or duplicate execution mechanisms, D6.4 establishes **one unified path** for all transformation execution:

```text
User Intent / Agent Request
        │
        ▼
[D4 Limo Agent Loop]  ──► LangGraphBridge.dispatch_next_stage("generate")
        │
        ▼
[TransformService.orchestrate_transformation(job_id)] ◄── SINGLE AUTHORITATIVE ENTRY POINT
        │
        ▼
[TransformationWorkflowOrchestrator.execute_job_workflow(job)]
        │
        ├─► [D5 CanonicalContent] (Single Source of Provenance Truth)
        │     ├── Markdown Adapter ──────► Real .md file + Artifact
        │     ├── HTML Adapter ──────────► Real .html file + Artifact
        │     ├── LinkedIn Adapter ──────► Real .md file + Artifact
        │     ├── Twitter Adapter ───────► Real .json file + Artifact
        │     ├── Infographic Adapter ───► Real .svg file + Artifact
        │     └── Contract Builder ──────► GenOffice / Video Payload (Guarded)
        │
        ▼
[TransformationWorkflowResult] (Structured Read-Only Outcome)
        │
        ▼
[D6.5 Job & Artifact Handoff] (Future: DB persistence, SSE streaming, UI links)
```

> [!IMPORTANT]
> **Consolidation of Execution Methods**:
> The existing D6.3 `execute_deliverable()` and `execute_native_deliverables()` methods on `TransformService` are unified:
> - `execute_native_deliverables()` is superseded by `orchestrate_transformation()`.
> - `execute_deliverable()` delegates internally to `orchestrator.execute_single_task()`.
> There is only one execution engine: `TransformationWorkflowOrchestrator`.

## 3. Detailed Architecture Addressing All 7 MUST-FIX Requirements

### 1. Real Data Flow: Independent CanonicalContent Execution (No Artificial DAG)
- **Principle**: In D6.3, all native adapters (`NativeMarkdownAdapter`, `NativeHtmlAdapter`, `NativeSocialAdapter`, `NativeInfographicAdapter`) and external contracts synthesize directly from `CanonicalContent`. Social posts and infographics do **not** depend on or consume the Markdown file.
- **Data Flow**:
  ```text
  CanonicalContent
   ├── Markdown Deliverable Task
   ├── HTML Deliverable Task
   ├── LinkedIn Deliverable Task
   ├── Twitter Deliverable Task
   ├── Infographic Deliverable Task
   └── External Contract Generation (Docs, Slides, Sheets, Video)
  ```
- **Execution Order**:
  - Tasks execute independently as sibling work units.
  - No false serialization or artificial dependency chain is introduced.
  - Tasks are processed in the natural order specified by the `OutputPlan` without blocking sibling formats.

### 2. Explicit Workflow Lifecycle & Dedicated Status for External-Only Workflows
To avoid ambiguous states where a job with only external deliverables is labeled "partially completed", we introduce an explicit `WAITING_EXTERNAL` status.

- **`WorkflowStatus` Enum**:
  - `PENDING`: Initialized, not started.
  - `RUNNING`: Actively processing tasks.
  - `COMPLETED`: All planned deliverables completed successfully (all were native, real artifacts generated).
  - `WAITING_EXTERNAL`: **All planned deliverables are external** (e.g. `[PRESENTATION, VIDEO]`). Their versioned contract payloads have been constructed and held; zero native deliverables were requested; zero tasks failed.
  - `PARTIALLY_COMPLETED`: **Mixed outcome**. At least one native deliverable produced a real artifact, while one or more deliverables are either waiting for external engines (`BLOCKED`) or failed.
  - `FAILED`: Fatal workflow error or all native deliverables failed with zero deliverables completed or waiting.
  - `CANCELLED`: Execution cancelled at task boundary.

- **`TaskStatus` Enum**:
  - `PENDING`: Awaiting execution.
  - `RUNNING`: Actively executing native adapter.
  - `COMPLETED`: Native deliverable produced a verified file and registered artifact.
  - `BLOCKED`: External engine deliverable; contract payload generated and held for D7/D8.
  - `FAILED`: Execution failed after retries exhausted.
  - `SKIPPED`: Task skipped due to workflow cancellation.

### 3. Realistic Cancellation Semantics (Task-Boundary Cancellation)
Native D6.3 adapters execute synchronously in Python (formatting strings, writing to disk, registering in SQLite) and cannot be forcibly interrupted mid-write without risking data corruption.

- **Defined Semantics**:
  - Cancellation operates strictly at **task boundaries**.
  - `TransformationWorkflowOrchestrator.cancel_workflow(workflow_id)` sets a cancellation flag on the workflow.
  - If a native task is currently executing (`RUNNING`), it runs to completion (completes in < 50ms) to ensure filesystem and database consistency.
  - All subsequent unstarted tasks in the workflow transition immediately to `TaskStatus.SKIPPED`.
  - The workflow terminates with `WorkflowStatus.CANCELLED`.
  - Completed artifacts generated prior to cancellation remain intact and accessible in the result.

### 4. Retry Idempotency: Identity Keyed by `(job_id, deliverable_id)`
- **Problem**: If an adapter writes a file but artifact registration or state persistence fails, retrying the task could leave orphaned files or duplicate artifact records.
- **Idempotency Guarantee**:
  - Execution identity is deterministic: `(job_id, deliverable_id)`.
  - Before invoking a native adapter retry:
    1. The orchestrator checks if an artifact already exists with metadata `{"job_id": job_id, "deliverable_id": deliverable_id}`.
    2. If found:
       - Checks if the physical file exists on disk and verifies its SHA-256 hash.
       - If valid, reuses the existing `Artifact` and avoids duplicate file synthesis.
       - If invalid or missing, cleans up the orphaned database record / stale file before re-running.
    3. Storage operations use deterministic pathing: `artifacts/{job_id}/{deliverable_id}/{filename}` (or atomic overwrite in `StorageService`), ensuring zero duplicate file accumulation across retries.

### 5. Safe User-Facing Error Messages (No Tracebacks in `task.error`)
- **Diagnostic Hygiene**:
  - In `DeliverableTask`:
    - `task.error`: Contains a sanitized, user-facing summary (e.g. `"Twitter synthesis failed: Character limit constraint exceeded"` or `"File storage error during Markdown deliverable write"`).
  - Internal tracebacks, local absolute paths, and system details are logged via Python `logger.exception()` for developer diagnostics (consistent with D3 logging guidelines) and are **never** exposed on `task.error`.

### 6. Frozen Structured Result Model
We define `TransformationWorkflowResult` as a frozen Pydantic model:

```python
class TransformationWorkflowResult(LimoBaseModel):
    """Structured, read-only result of a transformation workflow execution."""
    model_config = ConfigDict(frozen=True)

    workflow_id: str
    job_id: str
    plan_id: str
    canonical_id: str
    status: WorkflowStatus
    artifacts: List[Artifact] = Field(default_factory=list)
    blocked_contracts: Dict[str, Dict[str, Any]] = Field(default_factory=dict)
    failed_tasks: List[Dict[str, str]] = Field(default_factory=list)
    completed_deliverable_ids: List[str] = Field(default_factory=list)
    total_deliverables: int
    execution_time_seconds: float
```

- Any attempt to mutate the result after execution raises a Pydantic validation error.
- Acts as the immutable data contract handed to D6.5.

### 7. LangGraph Complementarity (No Competing Orchestration)
- `LangGraphBridge` (D4) remains the single macro-level pipeline bridge.
- `WorkflowStage.GENERATE` handler in `LangGraphBridge` calls:
  `transform_service.orchestrate_transformation(job_id)`
- `TransformationWorkflowOrchestrator` coordinates deliverable-level tasks within the `GENERATE` stage.
- Macro state is tracked in `WorkflowState`; deliverable state is tracked in `TransformationWorkflow`.
